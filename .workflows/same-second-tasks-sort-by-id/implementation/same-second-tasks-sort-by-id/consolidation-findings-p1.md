# Consolidation Findings: same-second-tasks-sort-by-id (Phase 1)

## Findings

### F1: Store.Mutate caches the mutated slice unnumbered while every parse of the written file numbers it
- **Class**: behaviour
- **Failure**: The phase splits one rule across three sites. Reads number unnumbered records in `ParseJSONL`, and each creation path must remember `task.NextSeq` on its own. `Store.Mutate` sits between them: it marshals and caches `mutated` as returned. If a mutation appends a task with `Seq` 0, the file stores no `seq` (`omitempty`) and the cache stores 0. The next read sees a matching `jsonl_hash`, so the cache is not refreshed, and the newest task lists *first* among same-second, same-priority peers. `tick ready --count 1` hands it out ahead of the first-authored task. This is the same silent wrong selection the feature exists to remove. It lasts until the next write renumbers the task, and meanwhile `tick rebuild` and `tick dep tree` (both parse the file) disagree with `tick list`. No test notices, because nothing appends an unnumbered task through the real store. Before this phase, `ParseJSONL(MarshalJSONL(x))` equalled `x`, so the cache always matched the file. This phase broke that equivalence for `Seq` 0 inputs. Today's two creation sites both call `NextSeq`, so the bug is latent. A scratch copy with `create.go:221` removed shows it concretely: the cache listed step-5 first, while every parse-based assertion passed. The obvious trap for the next creation path is the exported `task.NewTask`, which builds exactly such a task. It has been production-unused since before this phase.
- **Evidence**: internal/storage/store.go:187-206 (`fn` result goes straight to `MarshalJSONL` at :193 and `s.cache.Rebuild(mutated, …)` at :206; the :204 comment claims the cache is rebuilt "from the same bytes that were written"); internal/storage/store.go:412 and internal/storage/cache.go:273-275 (freshness keyed on the hash alone, so a seq-0 cache survives the next read); internal/storage/jsonl.go:116, :123-131 (backfill runs on parse only); internal/cli/create.go:221 and internal/migrate/store_creator.go:82 (per-site `Seq: task.NextSeq(tasks)`); internal/task/task.go:284-309 (`NewTask` returns a task with no `Seq`)
- **Proposed shape**: Call `backfillSeqs(mutated)` in `Store.Mutate` between :187 and :193. The file and the cache then always carry a number, and the cache equals a parse of the written bytes whatever the caller supplies. For an appended task, backfill assigns exactly `NextSeq` over the rest, so creation and backfill become one rule at one site. Verified in a scratch copy: with the call added, the full suite passes. It also passes the `cli` and `storage` suites with both per-site `NextSeq` calls removed. The only failures then are the two `mockStore` subtests at internal/migrate/store_creator_test.go:262-295, which assert on the mock's slice and never pass through `Mutate`. Keeping the per-site calls is harmless; dropping them means moving those two subtests onto a real store.
- **Bank**: "Store.Mutate rebuilds the cache from the mutated slice, not a parse of the written bytes, so an appended unnumbered task caches at seq 0" (reviewer, 1-4). Still real; its example path is gone, since Task 1-5 made `tick migrate` assign a seq at store_creator.go:82. "The sequence invariant depends on every task-creation site calling NextSeq; Store.Mutate does not backfill the mutated slice" (reviewer, 1-5).

### F2: The create-sequence subtests read stored sequences through the backfilling parser, so they pass with create's assignment deleted
- **Class**: near-miss
- **Failure**: `persistedSeqs` and the seq slice in the first subtest read tasks.jsonl through `readPersistedTasks` → `storage.ReadJSONL`. Task 1-3 wrote them when that reader returned the raw value. Task 1-4 then added backfill to `ParseJSONL`, which silently turned them into readers of the backfill, and wrote its own raw reader, `rawSeqs`, alongside. In a scratch copy with `Seq: task.NextSeq(tasks)` removed from create.go:221, four of the five `TestCreateAssignsSequence` subtests still pass: :61, :82, :96 and :124, all named for the sequence create stores. The missing assignment is caught only in another file (backfill_seq_test.go:114, :151, which use `rawSeqs`) and by the retry-driven ordering subtest at create_seq_test.go:144. The test named for create's numbering checks the reader, not create.
- **Evidence**: internal/cli/create_seq_test.go:26-33 (`persistedSeqs`), :67-78, :91, :104, :130, :138; internal/cli/create_test.go:49-57 (`readPersistedTasks` → `storage.ReadJSONL`); internal/cli/backfill_seq_test.go:23-43 (`rawSeqs`, the raw decode)
- **Proposed shape**: Make `persistedSeqs` decode each line's raw `seq` keyed by `id`, as `rawSeqs` does. Replace the slice at :67-78 with a raw read. Alternatively, collapse the two into a single raw reader returning ID→seq that both files use. If F1 lands, the written file always carries a number and a parse equals the raw bytes, so this dissolves. It stands on its own only if F1 is declined.
- **Bank**: "Create-sequence tests read stored sequences through the backfilling parser, so three no longer check what create writes" (reviewer, 1-4). The Task 1-5 half of that entry is absorbed: migrate_seq_test.go:70 and :91 already read through `rawSeqs`.
