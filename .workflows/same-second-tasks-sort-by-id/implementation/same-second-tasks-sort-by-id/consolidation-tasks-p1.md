# Consolidation Tasks: Same Second Tasks Sort By Id (Phase 1)

## Task 1: Number Every Task A Mutation Writes, And Check Stored Sequences Raw
placement: phase 1
severity: behaviour

**Problem**: The numbering rule runs on read (`ParseJSONL` backfill, internal/storage/jsonl.go:116, :123-131) and at each creation site (`task.NextSeq` at internal/cli/create.go:221 and internal/migrate/store_creator.go:82), but not in `Store.Mutate` (internal/storage/store.go:187-206), which marshals and caches the slice the mutation returns as-is. A mutation that appends a task with `Seq` 0 writes it with no `seq` and caches it at 0; the next read sees a matching `jsonl_hash` (store.go:412, cache.go:273-275) and keeps that cache, so the newest task lists first among same-second, same-priority peers and `tick ready --count 1` hands it out ahead of the first-authored task — the silent wrong selection this work removes — until the next write renumbers it, while `tick rebuild` and `tick dep tree` (both parse the file) disagree with `tick list`. Before this phase `ParseJSONL(MarshalJSONL(x))` equalled `x`, so the cache always matched the file; backfill-on-parse broke that for `Seq` 0 input, and the comment at store.go:204 ("from the same bytes that were written") no longer holds for it. Nothing appends an unnumbered task through the real store, so no test notices: a scratch copy with create.go:221's assignment removed cached step-5 first while every parse-based assertion passed. Latent today (both creation sites call `NextSeq`), but the exported `task.NewTask` (internal/task/task.go:284-309) builds exactly such a task. Separately, the create-sequence tests read stored sequences through `readPersistedTasks` → `storage.ReadJSONL` (internal/cli/create_seq_test.go:26-33, :67-78; internal/cli/create_test.go:49-57), which now backfills, so four `TestCreateAssignsSequence` subtests (:61, :82, :96, :124) pass with create's assignment deleted — the test named for what create stores checks the reader instead. The deletion is caught only in another file (internal/cli/backfill_seq_test.go:114 and :151, which read through `rawSeqs`) and by the retry-driven ordering subtest at create_seq_test.go:144.
**Solution**: Number the mutated slice in `Store.Mutate` before `MarshalJSONL` with the same backfill `ParseJSONL` runs, so every write stores a number for every record and the cache equals a parse of the written bytes whatever the caller supplied; for an appended task this assigns exactly `NextSeq` over the rest, so creation and backfill stay one rule. Keep the per-site `NextSeq` calls in create and migrate — removing them buys no behaviour and would force the mock-store subtests (internal/migrate/store_creator_test.go:262-295) onto a real store. Add a real-store test that appends an unnumbered task through `Mutate` and asserts the stored `seq`, the cache's `seq` column and the listed order. Switch the create-sequence tests' stored-sequence reads to a raw decode of each line's `seq`, as `rawSeqs` does (internal/cli/backfill_seq_test.go:23-43), so they check the bytes written rather than the read-time backfill.
**Outcome**: No write can leave an unnumbered record in `tasks.jsonl` or a zero `seq` in the cache, a future creation path that forgets `NextSeq` is still ordered correctly, and the create-sequence tests fail when create's stored sequence is wrong.

**Acceptance Criteria**:
- [ ] Given three records carrying `seq` 1, 2, 3 at one creation second and one priority, a `Store.Mutate` on a real store that appends a task with no sequence — same second, same priority, an ID sorting ahead of all three — writes that record to `tasks.jsonl` carrying `seq` 4, and the cache's `seq` column holds 4 for it (§2.2, §3.2)
- [ ] Straight after that mutation, with no further write, `tick list` lists the appended task last of the four, and `tick ready --count 1` returns the first-authored task rather than the appended one (§1.2, §8.1)
- [ ] After that mutation, `tick rebuild` leaves every task's cached `seq` as the mutation cached it, and `ReadTasks` — the path `tick dep tree` reads — returns the same numbers: the cache equals a parse of the written bytes (§2.3)
- [ ] A mutation returning records numbered 1, 2, 3, then two records with no sequence, then records numbered 4 and 5 writes the two unnumbered records as 6 and 7 in record order and leaves every carried number unchanged — the rule `ParseJSONL` applies on read (§2.1, §2.3)
- [ ] Every sequence assertion in `TestCreateAssignsSequence` reads the `seq` each record carries in `tasks.jsonl`, not a value `storage.ReadJSONL` backfilled, so a record written without a `seq` reads as 0 and fails it
- [ ] The rest of the suite passes unchanged, including the create and migrate `Seq: task.NextSeq(tasks)` assignments and the migrate `mockStore` subtests (§8.5)
