# Consolidation Tasks: Free Text Round Trip (Phase 8)

## Task 1: The Focused Dependency View's Edge List Is Also The Relation
placement: phase 8
severity: behaviour

**Problem**: `Tfree-text-round-trip-8-1` made the full-graph `dep_tree` rows relational — one per stored dependency, derived from `BlockedBy` via `collectStoredEdges` — and left focused mode building `blocked_by`/`blocks` from the walk (`internal/cli/toon_formatter.go:210-211` calling `collectUpstreamEdges`/`collectDownstreamEdges` at `:217-235`). Before that task both modes walked and agreed; the phase created the split, so one command now emits `from,to` rows under two different rules depending on whether an id was named. Reproducer: A unblocked, B and C blocked by A, D blocked by B and C, E blocked by D — five stored dependencies. `tick dep tree --toon` returns five rows; `tick dep tree A --toon` returns six, with `tick-D,tick-E` twice, because the walk reaches D by two paths and re-emits everything below it. An agent that builds a graph from the focused document double-counts a dependency exactly as it did from the full graph before 8-1, and nothing in the document says which rule produced the rows. `README.md:321`, written by this phase, promises "the toon edge list carries one row per stored dependency" with no scoping to the full graph, so the shipped documentation is false for the focused form.

**Solution**: Derive the focused sections from the relation as well, restricted to the neighbourhood the walk reaches: `blocked_by` carries one row per stored dependency among the target's transitive blockers, `blocks` one per stored dependency among its transitive dependents, each in record order and neither repeating. Transitivity is preserved — the sections still reach the whole chain, which is what focused mode exists to show — and only the repetition goes. The `DepTreeNode` trees stay untouched for pretty and JSON, where drawing a shared task under each of its blockers is a picture rather than a duplicated fact, exactly as 8-1 left the full graph. Settled rather than staged: §8 already holds that the counts and the edge list never disagree, and §1's bar is output an agent can read without a rule learned outside it — a command whose two forms count the same dependency differently fails both, and 8-1 answered the identical question for the full graph two tasks ago. The alternative the finder weighed — scoping the README sentence to the full graph and leaving focused mode repeating — documents the defect instead of removing it. This changes shipped output, so it is recorded as a dated corrigendum against §8 alongside the other dep-tree output changes; the specification record is the orchestrator's to write, not the task's.

**Outcome**: `tick dep tree <id> --toon` carries one row per stored dependency in the target's neighbourhood, in both sections, and an agent's count from the focused document agrees with its count from the full graph and with `tick show`.
