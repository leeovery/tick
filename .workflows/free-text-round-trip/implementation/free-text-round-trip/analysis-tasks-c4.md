# Analysis Tasks: free-text-round-trip (Cycle 4)

## Task 1: The Field Selection Narrows Each List Section Once
severity: duplication
sources: duplication

**Problem**: `selectedItems(detail.X, sel.Positions(fieldX))` is written out fifteen times — once per list section per formatter (`internal/cli/toon_formatter.go:78`, `:83`, `:88`, `:93`, `:98`; `internal/cli/json_formatter.go:115-118`, `:127`; `internal/cli/pretty_formatter.go:158`, `:187`, `:192`, `:197`, `:202`) — and the pairing of a collection with the field name that selects it exists only in those fifteen expressions. Nothing type-checks the pairing: `detail.Refs` with `sel.Positions(fieldTags)` compiles, and a section taken whole compiles. The one guard over the three formatters, `TestRegisteredFieldRendering` (`internal/cli/show_fields_test.go:760`), asserts only that each format renders something non-empty for each registered name, so it passes unchanged when a format ignores positions and renders the whole section. The failure that escapes: an agent runs `tick show <id> --field notes.2` under one format, is handed a different note than under another, believes the note it read is the note it asked for, and runs `tick note remove <id> 1` against a position that does not hold it — the loss §6.3 introduced the index column to prevent. Nothing fails: the document parses, the command exits 0, and §11's conformance drivers assert only that it decodes. Noticed as a deleted note nobody asked to delete.

**Solution**: Resolve the narrowing once, beside `TaskDetail` in `internal/cli/format.go`: an unexported value carrying the narrowed `Tags`, `Refs`, `BlockedBy`, `Children` and `Notes` plus the note positions, produced by a method on `TaskDetail` that applies `d.Fields`, with `ToonFormatter.FormatTaskDetail`, `taskDetailJSONObject` and `prettyDetailHeader`/`prettyDetailBlocks` reading the values they render from it rather than calling `selectedItems` themselves. The field-name-to-collection pairing then lives in one function, beside the `showFields` registry that already pairs the names with their value accessors. What stays per formatter is the rendering — a toon table, a JSON array, a pretty block — and the gates (`sel.includes(...)`, the non-empty tests), which differ legitimately by format; only the narrowing that precedes them moves. Behaviour-preserving: output is byte-identical in all three formats, filtered and full, and the existing suites stay green. This extends phase 4's settled direction rather than touching it — task 4-3 put each field's declaration in the registry once and task 4-4 pointed the formatter gates at the registry's names; the name-to-collection pairing is the one part of that vocabulary still restated per formatter.

**Outcome**: Adding a list section to the detail document, or respelling one, is a single edit that reaches all three formats, and a collection paired with the wrong field name is a single mistake in one place rather than a silent divergence between formats.

## Task 2: A Refusal Names The Task Carrying The Refused Value, Not The Document's Subject
severity: medium
sources: standards

**Problem**: §3.1 requires the diagnostic to name "the field or section it could not encode and the task that carries the refused value", with the section name alone standing only "where the offending row cannot be identified". Phase 9's row-identity mechanism (`encodeToonSectionIdentified` plus `sectionRefusal`, `internal/cli/toon_formatter.go:346-372`) was wired to `FormatTaskList` alone. `buildRelatedSection` (`blocked_by`, `children`, `:300`) and `buildChangedSection` (`:150`) still call the identity-less `encodeToonSection`, and `refusalForTask` (`:392`) then overwrites whatever `taskID` the error holds with the document's subject, so even a future identity would be discarded. Reproduced against a binary built from the working tree: a clean-titled parent with a child whose title carries an escape gives `tick --toon show <parent>` → `Error: cannot encode section children of task <parent> as TOON: toon: unsupported control character U+001B in string`, and `tick --toon done <parent>` the same for `section changed`; the child's ID appears nowhere. An agent acts on the ID it was handed, re-runs `tick show` on it, gets the identical error, and is left with the routes §1 opens this work to delete — switching format or reading `.tick/tasks.jsonl` — while believing it has already located the culprit. Naming the wrong task is worse than naming none, because the ID reads as an answer. Every row of `blocked_by`, `children` and `changed` carries a task ID, so the condition §3.1 attaches to the section-name-only fallback is not met on any of the three.

**Solution**: Give the three sections whose rows are other tasks a row identity — `buildRelatedSection` and `buildChangedSection` passing the row's ID to the identity-taking encoder the task list already uses — and stop `refusalForTask` clobbering an identity the refusal already carries, overriding only when `refusal.taskID` is empty. A section whose rows have no identity of their own (`notes`, `tags`, `refs`) still names the document's subject, as today, and a refused field on the subject itself is untouched. This changes the direction pinned by step 4 of phase 9's staged task and by the subtest at `internal/cli/toon_refusal_test.go:231` ("it names the document's subject when the refused value sits on a cascaded task"), which asserts the cascaded child's ID is *absent* from stderr: that subtest is rewritten to assert the child is named, and the matching acceptance criterion is superseded. Grounds: §3.1 was amended after that direction was set and is the later and governing statement, the departure is measured against a built binary, and the amended sentence is unqualified — it scopes task-naming to the task carrying the value, not to the document's subject.

**Outcome**: Every TOON refusal names a task the agent can act on directly — the offending row for a task list, a related section and a cascade table, the document's subject for a section whose rows carry no ID — so no refusal hands back an ID that does not carry the refused value.

## Task 3: One Enumeration Of The Stored Dependency Edges
severity: near-miss
sources: duplication

**Problem**: `collectStoredEdges` (`internal/cli/dep_tree_graph.go:184`) and `collectScopedStoredEdges` (`:196`) both walk `tasks` in slice order and each task's `BlockedBy` in stored order, emitting one `DepTreeEdge{From: dep, To: t.ID}` per entry; the scoped one adds a membership test on each end and nothing else, and their doc comments restate the ordering rule word for word. A change to the enumeration rule made in one and not the other makes `tick dep tree` and `tick dep tree <id>` report different edges for the same stored dependencies. Both documents parse, each agrees internally with its own counts, and each function's tests keep passing, so nothing reports it; an agent reconciling the project view with the focused view is told the store holds two different graphs. The divergence is not hypothetical: §8's corrigendum of 2026-09-20 records this rule diverging once already between the full graph and the focused view — five stored dependencies coming back as five rows from one and six from the other — which is what a single enumeration exists to prevent.

**Solution**: Keep one enumeration: have `collectStoredEdges(tasks)` delegate to the scoped form with a scope that keeps every ID — a nil ID set read as "no scope", or a keep predicate — so record order and one-row-per-`BlockedBy` are stated once and the scope filter is the only thing the focused form adds. Behaviour-preserving: both callers emit the same rows in the same order as today, and the dep-tree suites stay green unchanged. This completes the settled direction of phase 8's task 1 and cycle 2's task 1 — both views derive their rows from the stored relation — rather than touching it; those tasks made the two forms agree, and this makes them agree by construction.

## Task 4: The Field Selection Type Answers A Nil Receiver One Way
severity: drift
sources: architecture

**Problem**: `*FieldSelection` documents nil as "the whole document" and three of its five methods honour it — `includes`, `Positions` and `ValidatePositions` all return sensible values on a nil receiver. `Len` and `Only` (`internal/cli/show_fields.go:165-192`) dereference the receiver; verified against the working tree, either panics with `runtime error: invalid memory address or nil pointer dereference`. `detail.Fields` is nil on every document `create`, `update`, `note add`, `note remove` and an unfiltered `show` produce (`internal/cli/format.go:236`), and all three formatters hold that pointer. The one compensating check is `bareFieldValue`'s `if sel == nil` at `internal/cli/show_fields.go:119` — in a caller, not in the type — so correctness rests on caller discipline: the first production code that asks the selection its size, the natural question given `Only` exists, crashes the CLI with a Go stack trace on the commands an agent runs most, instead of printing the task. `Len` has no production caller at all today, so the split has been carried this far untested from the production side.

**Solution**: Give `Len` and `Only` the nil handling the other three already have — `Len` returning 0, `Only` returning `("", false)` — and drop the `if sel == nil` guard from `bareFieldValue`, which the type then covers. Behaviour-preserving: `bareFieldValue` returns `("", false)` for a nil selection exactly as it does now, and no other caller changes. Settled rather than staged, on the record: phase 4's task 3 already chose one nil-safe gate for this type when it deleted the exported `Selected` in favour of nil-safe `includes`; extending that convention over the two methods it did not reach is the same move. `Len` is kept rather than deleted — it is exercised by the type's own tests, and deleting it trades the contract fix for a test rewrite that buys nothing. The architecture finding's second half — unexporting the type's methods — is not carried: visibility and naming are below the finding floor.

**Outcome**: The nil-means-whole-document convention is a property of the type rather than of its callers, so a formatter reaching for the selection's size on a document with no selection gets an answer instead of a stack trace.

## Task 5: Corrections
severity: corrections
sources: standards

**Problem**: `README.md:494` describes the pre-`Tfree-text-round-trip-9-2` refusal diagnostic: a refused value is reported "naming the field or section it could not encode — and the task, where the document covers one". `tick list`, `tick ready` and `tick blocked` cover many tasks, so that clause tells a reader the ID will not be in the message; the shipped behaviour since that task names it (pinned at `internal/cli/toon_refusal_test.go:163`). A reader who believes the README goes looking for the row by bisection or in `.tick/tasks.jsonl` — the route §3.1's amendment was written to remove — with the answer already sitting in the error they dismissed. §12.1 holds the README to what the tool produces.

**Solution**: One edit, `README.md:494` — replace the restriction clause "— and the task, where the document covers one —" so the sentence states §3.1's rule in full: the diagnostic names the field or section it could not encode and the task carrying the refused value, the offending row where the document is a task list, with the section name alone standing only where no row can be attributed. Keep the sentence that follows ("The value is stored and read back intact either way…"), which is accurate. Wording is the author's; the rule is the spec's, so the paragraph is true of shipped behaviour with or without Task 2, which removes the one remaining branch where the code departs from it.
