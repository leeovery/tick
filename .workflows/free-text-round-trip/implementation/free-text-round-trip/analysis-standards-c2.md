- FINDING: A dependency participant another seed reaches still seeds its own top-level tree, so `dep tree` repeats a chain
  SEVERITY: medium
  FAILURE: In a project holding an orphaned dependency one level above a real chain — task X blocked by Y, Y blocked by an ID no task carries — `tick dep tree` prints `dep_tree[3]{from,to}:` for a two-edge graph, repeating `Y,X`, and pretty draws the whole `Y → X` chain twice: once as a top-level entry and once nested under the ghost. An agent counting or walking the edge list double-counts the dependency; a terminal reader sees Y presented as a top-level tree although Y is blocked, which is the one thing a top-level entry is supposed to rule out. `internal/doctor/orphaned_dependency.go` exists because the project expects this state, and before this work neither the ghost nor the chain reached the output at all, so the whole rendering is new with it. Verified against a binary built from HEAD.
  FILES: internal/cli/dep_tree_graph.go:225, internal/cli/dep_tree_graph.go:226, internal/cli/dep_tree_graph.go:144, README.md:321
  DESCRIPTION: §8's corrigendum widened the full-graph edge list so "after the walk from the roots, any participant not yet emitted seeds a further walk". `buildSeededTrees` walks `orderedParticipants` in first-seen order and skips only a participant already emitted by an *earlier* tree, so a participant a *later* seed would have reached is seeded first and then emitted a second time inside that later tree. `collectParticipants` adds a blocked task before its blockers, so the blocked-but-blocking middle of a dangling chain is always visited before the dangling blocker that reaches it — the ordering makes the redundant seed the normal case rather than a corner. This is not the documented diamond duplication: a diamond repeats a node that genuinely has two paths, whereas here Y has exactly one path and is still rendered twice, and README.md:321 states the rule the output breaks ("the pretty tree draws root tasks (tasks that block others but aren't blocked themselves) with their downstream chains, then the tasks no root reaches"). No test pins the current shape — `dep_tree_graph_test.go`'s dangling-blocker case is one task directly under the ghost, where the ordering never bites.
  RECOMMENDATION: Seed only participants that no other seeded tree reaches: hold back a participant that an unemitted participant blocks, and fall back to seeding the first remaining participant when a pass emits nothing, which is what keeps a cycle — where every member is blocked by another member — covered exactly as it is today. Cover it with the two-level dangling chain above, which is the shape that exposes the ordering.
