ISSUES:
- `internal/cli/show_fields.go:93-99` — `addPosition` appends unconditionally, so a repeated position is stored repeatedly. Confirmed by execution: `--field notes.2,notes.2,notes.3,notes.2` yields `positions["notes"] = [2 2 3 2]`, and `--field notes.3 --field notes.3` yields `[3 3]`. The task's own solution statement is "recognised names only, optional 1-based positional suffixes on list sections, whitespace trimmed, repeats collapsed", and §9.1 (spec line 346) is "A field named more than once renders once". Names are deduplicated (`record` at line 81-85) but positions are not, so the contract holds at one granularity and not the other. Failure it prevents: an agent that builds the flag value programmatically and repeats `notes.2` gets `notes[2]{index,text,created}:` with note 2 emitted twice — noticed as a duplicated row, and only if Task 3's renderer happens not to iterate items instead of positions. Leaving it makes a spec rule depend on a sibling task's choice of loop rather than on the parser that claims to have validated the selection.
  FIX: in `addPosition`, skip a position already recorded — after the `s.whole[name]` guard, `if slices.Contains(s.positions[name], pos) { return }` (`slices` is already the idiom in this package's tests and `maps` is already imported in `flags.go`). Add one subtest alongside `"it collapses a repeated name"`, e.g. `"it collapses a repeated position"` asserting `--field notes.2,notes.3,notes.2` gives `Positions("notes") == []int{2, 3}`.
  ALTERNATIVE: leave the parser as-is and require Task 3's renderer to iterate section items and test membership, which collapses duplicates and fixes ordering as a side effect. That works but puts a spec rule in the renderer where it is invisible and unpinned, and every future consumer of `Positions()` has to re-derive it. The reviewer recommends the parser fix — one line, in this task's own new file, and it makes `Positions()` mean what its name implies.
