# Consolidation Findings: free-text-round-trip (Phase 4)

## Findings

### F1: `tick help show` fuses the flag label into its description
- **Class**: behaviour
- **Failure**: A user or agent running `tick help show` reads `  --field, --fields <name,...>Select fields by name; a section may be narrowed with .N (e.g. notes.2)` — argument spec and description glued with no separator. `show`'s only flag entry is its entire Flags block, so the command help reads as garbled, and `tick help --all` (the agent discovery surface) prints the same fused line. Noticed by eye the first time anyone runs either command. §12.1 makes the help text a deliverable of this work, and the flag has to be discoverable for the field-selection surface to be usable at all.
- **Evidence**: `internal/cli/help.go:308` and `internal/cli/help.go:286` both format with `"  %-24s%s\n"`, which loses the gap entirely for any label wider than 24 columns. The label added by this phase, `internal/cli/help.go:75`, is 28 columns. Measured on a build of `7c8cac7c`:
  - `tick help show` → `  --field, --fields <name,...>Select fields by name; …`
  - `tick help --all` line 30 → `  --field, --fields <name,...>Select fields by name; …`
  The same overflow already existed for `internal/cli/help.go:44` (`--type <bug|feature|task|chore>`, 31 columns), but `create` has eight flag lines and only one is fused; `show` has one, and this phase created it.
- **Proposed shape**: Give the flag column a minimum two-space gap, or compute the column from the widest label in the set being printed. The two renderers duplicate the label-building and the format string; extract one `flagLabel`/`writeFlagLines` helper and change it once. The remedy shifts the rendered help of `create`, `list`, `remove`, `migrate` and `--all`, so the help expectations across the suite move with it — that reach outside the phase diff is expected.
- **Bank**: Confirmed — executor and reviewer entries on `free-text-round-trip-4-1`, both naming `help.go:308` and the 28-column `show` label.

### F2: The fifteen field names exist as five independent sets of bare literals, and nothing ties them together
- **Class**: drift
- **Failure**: A name added to (or respelled in) the recognition registry is accepted by the parser but silently unrendered by any formatter whose gate literal was not updated in the same edit. `tick show <id> --field <name>` then prints zero bytes and exits 0 in that format while another format prints the field — no compile error, no failing test. The user or agent reads the empty output as "this task has no value for that field", which is exactly the human-surface/agent-surface divergence §9.7 exists to close. Noticed only by a caller comparing two formats.
- **Evidence**:
  - Registry (canonical 15 names): `internal/cli/show_fields.go:34-50`
  - Toon gates: `internal/cli/toon_formatter.go:75, 80, 85, 90, 95, 103` and the `add(...)` calls in `buildTaskSection` at `internal/cli/toon_formatter.go:257-274`
  - JSON gates: `internal/cli/json_formatter.go:128-152`
  - Pretty gates: `internal/cli/pretty_formatter.go:151-174` and `:186-210`
  - `internal/cli/show_fields_test.go:117-133` — the subtest named "it recognises every registered name" iterates a hardcoded list of the 15 names rather than `showFields`, so a name added to the registry is not checked by the guard whose name claims to check it.
  - The inverse drift already exists: `internal/cli/toon_formatter.go:99` gates on `sel.includes("changed")`, a name no registry entry can ever select (`--field changed` is an unrecognised-name error). JSON drops `changed` under a selection (`internal/cli/json_formatter.go:119-158` never adds it) and pretty appends it regardless of the selection (`internal/cli/pretty_formatter.go:234-238`) — three different answers for one section key.
- **Proposed shape**: One ordered set of name constants shared by the registry and all three formatter gate lists, so a typo is a compile error. Drive `show_fields_test.go:117` off `showFields` itself. Add one table-driven parity assertion: for every name in `showFields`, a fixture carrying every field renders non-empty output in toon, pretty and JSON — which is what turns a registry name with a missing gate from silence into a test failure. Settle `changed` while there: either register it or drop the gate.
- **Bank**: Confirmed — two reviewer entries on `free-text-round-trip-4-5` (the bare-literal registry/formatter repetition, and the "four independent sets with nothing tying them together" restatement); the name facet of the `4-6` entry folds in here.

### F3: Two registries describe the same five list sections, and only one of them validates positions
- **Class**: duplication
- **Failure**: A list section added to `showFields` without a matching `showSections` entry is accepted with a positional suffix and never range-checked: `--field <section>.99` silently returns an empty or whole section and exits 0, instead of §9.6's out-of-range error. The reverse — an entry in `showSections` with no `items` accessor — silently makes a lone position return the section rather than the bare value. Neither divergence is a compile error, and coverage is written per section (`internal/cli/show_fields_test.go`, `list_show_test.go` subtests are named per section), so nothing fails. The agent acts on the wrong item or on a false claim about the data.
- **Evidence**: `internal/cli/show_fields.go:45-49` carries `kind`/`items` per list section (`items` deliberately nil for `children` and `blocked_by`, which hold rows); `internal/cli/show_fields.go:54-64` separately carries `name`/`noun`/`length` for the same five sections, consumed only by `ValidatePositions` at `internal/cli/show_fields.go:277-290`. The two tables were authored by different tasks (`items` by `4-6`, `showSections` by `4-7`) and agree today only by hand.
- **Proposed shape**: Fold `noun` and `length` onto `showField` for the list kinds and derive the validation walk from a single ordered slice of list-section names, so a section is declared once. Keep the document-order property explicit (it is toon's order, which the error message ordering depends on).
- **Bank**: Confirmed — reviewer entry on `free-text-round-trip-4-6` ("the registry and the three formatters each hold their own copy of where a section's data lives"); its data-accessor facet is this finding, its name facet is F2.

### F4: The filtered JSON document orders its keys alphabetically instead of in document order
- **Class**: behaviour
- **Failure**: `tick show <id> --json --field type,tags` returns `{"tags": …, "type": …}` while `tick show <id> --json` returns `type` before `tags`; `--field status,title,id` returns `id, status, title` against the full document's `id, title, status`. Toon and pretty both preserve document order under a selection, so the three formats disagree, and README.md:191 — written by this phase — tells the reader the filtered document comes back "in normal output order rather than the order they were typed". A caller diffing a filtered document against a full one, or holding a golden JSON fixture, gets a reordering nothing warned them about. No test catches it: `internal/cli/json_formatter_test.go` asserts key *sets* (`assertJSONKeySet`) and the "it keeps key order stable" subtest only compares two identical renders, which map marshalling satisfies for free.
- **Evidence**: `internal/cli/json_formatter.go:119-158` builds `map[string]any`, and `encoding/json` sorts map keys; the full path at `internal/cli/json_formatter.go:84-115` marshals the ordered `jsonTaskDetail` struct (`:59-78`). Measured on a build of `7c8cac7c`:
  - `tick --json show <id>` → `id, title, status, priority, type, tags, refs, notes, description, created, updated, blocked_by, children`
  - `tick --json show <id> --field type,tags` → `tags, type`
  - `tick --json show <id> --field title,notes.2` → `notes, title`
  Alongside the ordering, the two paths independently encode the §9.6 rule "a filtered key carries what full output carries for it": key presence, the `parent`/`closed` omit-when-absent behaviour and the empty-array/empty-string shapes are written twice (`:91-107` vs `:128-152`). A change to one is silent in the other. Toon and pretty avoid this by gating in place rather than forking a second renderer.
- **Proposed shape**: Render JSON from one ordered key table, gated per key, so full and filtered output share the order and the per-key rule. An ordered emission (an ordered key/value slice, or filtering a marshalled full document back into canonical order) replaces the map. Pin the order in a test, not just its stability.

### F5: `Selected` and `includes` are two gates over one question with opposite nil behaviour
- **Class**: drift
- **Failure**: `TaskDetail.Fields` is nil for every document `create`, `update`, `note add` and `note remove` produce. `includes` (`show_fields.go:166-168`) treats nil as "the whole document"; the exported `Selected` (`show_fields.go:160-162`) dereferences the receiver and panics on nil. A formatter path that reaches for the exported gate — the natural one to reach for, since it is the exported half of the pair — turns a mutation command into a runtime panic instead of a document. Noticed as a CLI crash in the field, not at compile time.
- **Evidence**: `internal/cli/show_fields.go:160-168` (the pair); `internal/cli/json_formatter.go:123` is the only production caller of `Selected`, and it is safe only because `FormatTaskDetail` branched on `detail.Fields != nil` first at `:85`; the other eight production gate sites use `includes` (`internal/cli/toon_formatter.go:75, 80, 85, 90, 95, 99, 103, 252`, `internal/cli/pretty_formatter.go:146, 186, 191, 196, 201, 210`). Nothing outside package `cli` uses `FieldSelection`, so the export buys nothing.
- **Proposed shape**: One nil-safe gate. Make `Selected` nil-safe and delete `includes` (or keep `includes` and unexport/remove `Selected`), routing every site through it. This lands naturally with F4, whose remedy retires the `Selected` call site anyway.
- **Bank**: Confirmed — reviewer entry on `free-text-round-trip-4-3`; it asked for the decision at the phase boundary once 4-4 and 4-5 had landed their gates, which they now have.

### F6: `showFieldScalar` and `showFieldDescription` are a distinction nothing reads
- **Class**: dead-code
- **Failure**: A maintainer adding a rule keyed on `showFieldScalar` — a plausible shape for any later work on bare values — silently excludes `description`, the sole member of a kind that behaves identically to it. A wrong `--field description` result, with no compile error and no failing test to flag it.
- **Evidence**: Kinds declared at `internal/cli/show_fields.go:12-19` and assigned across the registry at `:35-49`, but only `showFieldUnknown` (`:220`) and `showFieldList` (`:226`) are ever compared; `bareFieldValue` branches on `bare == nil` (`:124`) rather than on kind. Tasks 4-6 and 4-7 did not give the distinction a job.
- **Proposed shape**: Collapse `showFieldDescription` into `showFieldScalar`. The remaining distinction is list vs not-list plus registry presence, so the kind can reduce to a boolean on `showField` with recognition driven by the map lookup's `ok` — which also removes the `showFieldUnknown` zero-value convention.
- **Bank**: Confirmed — reviewer entry on `free-text-round-trip-4-3`.

### F7: The two README bare-value samples are documented output that nothing verifies
- **Class**: behaviour
- **Failure**: A later change to the bare-value path — an added trailing newline, a prefix, quoting, a different resolution for `notes.2` — leaves README.md:185-189 and README.md:204-207 describing output the tool no longer produces, and the whole suite stays green. Nobody notices until a user or agent copies the sample and gets something else: precisely the defect §12.1 names the README work as existing to prevent. Every other `$ tick` sample in the README is pinned byte-for-byte, so the gap is invisible to a reader of the test file.
- **Evidence**: `internal/cli/readme_samples_test.go:329-333` adds one field-selection sample, the multi-name toon document. The two bare-value fences — `$ tick show tick-a1b2 --field description` (README.md:185-189) and `$ tick show tick-a1b2 --field notes.2` (README.md:204-207) — appear in no `readmeSampleGroup`. `readmeSample` compares a fence body to stdout byte-for-byte and its `format` field is inert for a bare value, which is itself the §9.7 claim worth pinning, so both blocks fit the existing table unchanged. Task `4-8` was explicitly instructed to leave them out. Phase 6's `free-text-round-trip-6-4` pins bare-value bytes against the tool but not against the README, so no later task closes this.
- **Proposed shape**: Add both fences to `readmeSampleGroups` against the existing `fieldSelectionTasks` fixture, which already carries the description and the two notes the samples print. Optionally close the class rather than the instance: assert that every `$ tick`-prompted fence in the README is claimed by some `readmeSample`, with the one error-output sample (README.md:634) declared as an exemption.
- **Bank**: Confirmed — reviewer entry on `free-text-round-trip-4-8`.
