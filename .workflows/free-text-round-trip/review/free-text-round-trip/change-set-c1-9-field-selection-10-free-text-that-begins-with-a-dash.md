FINDINGS:
- [out-of-scope] internal/storage/jsonl.go:95 — a description long enough to push a JSONL line past `bufio.Scanner`'s default 64 KiB token limit is written to `.tick/tasks.jsonl` and then makes the whole project unreadable, and `tick doctor` denies it. Measured with the HEAD binary in a fresh project: `tick create "big" --description <70000 chars> --quiet` exits 0 and prints the new ID, `.tick/tasks.jsonl` holds one 70146-byte line, and every later command fails — `tick list` → `Error: failed to parse tasks.jsonl: error reading JSONL data: bufio.Scanner: token too long`, exit 1, the same for `tick stats` and `tick rebuild` — while `tick doctor` prints "✓ JSONL syntax: OK … No issues found", exit 0, because `ScanJSONLines` (internal/doctor/jsonl_reader.go:37) never consults `scanner.Err()` before returning at :65, unlike `ParseJSONL`, which does at internal/storage/jsonl.go:112. §10.3 declines an input path partly on the grounds that "an arbitrarily large description remains possible in principle"; in tick it is not — past ~64 KiB it destroys the store. Pre-existing and not caused by this work: reproduced identically with a binary built from eb88e700^ (5a71cbc8), and no commit in the range touches internal/storage or internal/doctor. The fix is planned work rather than an edit here — raise the buffer on both scanners (`scanner.Buffer`), have the doctor reader report `scanner.Err()` so the check stops lying, and decide whether the write path caps description length at all — so it is the user's to take or leave. FAILS: an agent or user who pastes a large description loses access to every task in the project, with the built-in diagnostic reporting the store healthy, and no route back but hand-editing tasks.jsonl.
