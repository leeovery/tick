FINDINGS:
- FINDING: Doctor throws away its failed scan and has every check read the file again
  SEVERITY: medium
  FAILURE: The failure is a mid-read I/O fault that doesn't repeat on every read, such as a failing disk or mount. That is the case the incomplete-read path exists for (spec 5.3). When that fault hits, an agent running `tick doctor` gets a report that contradicts itself. Some line-consuming checks fail with "tasks.jsonl could not be read in full", while others pass because their own re-read went through. The Cache check can also advise "Run `tick rebuild` to refresh cache" in the same report, which breaks 5.5's rule that no output points at rebuild while the read is incomplete. I reproduced this with a go test -overlay scratch test that used the WithTasksOpener seam, with an opener that failed on odd calls. The file was opened 12 times. Five checks passed, five failed with the read error, and the Cache check printed the rebuild advice. The agent sees mixed pass/fail verdicts next to a rebuild suggestion. The existing tests can't catch this because their seam fails the same way on every open.
  FILES: internal/cli/doctor.go:28, internal/cli/doctor.go:30, internal/doctor/jsonl_reader.go:87, internal/doctor/jsonl_reader.go:91, internal/doctor/cache_staleness.go:86, internal/doctor/helpers.go:30
  DESCRIPTION: The scan outcome is split across two packages. cli.RunDoctor scans once but shares only a success: it puts the lines in context under JSONLinesKey and drops the error. When the scan fails, doctor.getJSONLines finds no lines in context and calls ScanJSONLines again. It does this separately for each of the ten line-consuming checks and once more for refreshSuggestion. So the 5.3/5.5 guarantees (every line-consuming check fails with *that* read error, and no rebuild advice appears during an incomplete read) only hold if the I/O failure repeats identically across 11 more open-and-read passes. The guarantees depend on how the fault behaves rather than on the code. On any persistent failure the design also reads a file that just failed 11 more times.
  RECOMMENDATION: Share the whole scan outcome once. Store the lines and the error together (for example a scan-result value set through one doctor-owned helper such as `doctor.WithScan(ctx, lines, err)`, replacing the lines-only JSONLinesKey write in RunDoctor), and have getJSONLines return the stored error instead of re-scanning when a result is present. Every check and refreshSuggestion then judges the same read. The per-check fallback in linesUnavailableResult keeps its current shape. ScanJSONLines stays the fallback only when no scan has been run, for a check run on its own.
SUMMARY: The shared line reader, the store's DecodeTaskLine used by doctor's JSONL check, the parse-before-delete order in Rebuild, and the description cap at each route all fit together cleanly. One design issue remains: RunDoctor shares only a successful scan, so each doctor check re-reads the file after a failed read. With a read fault that doesn't repeat every time, the report contradicts itself and can advise `tick rebuild` during an incomplete read. I reproduced this with a scratch test.
