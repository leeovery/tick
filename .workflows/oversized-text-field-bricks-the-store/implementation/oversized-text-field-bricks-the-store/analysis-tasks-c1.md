# Analysis Tasks: Oversized Text Field Bricks The Store (Cycle 1)

## Task 1: Doctor shares one scan outcome, failure included, with every check
severity: medium
sources: architecture

**Problem**: `RunDoctor` scans `tasks.jsonl` once (`internal/cli/doctor.go:28`), but it puts the lines in context only when the scan succeeded (`:29-31`) and drops the error. When that scan fails, `getJSONLines` (`internal/doctor/jsonl_reader.go:87-92`) finds nothing in context and runs `ScanJSONLines` again. It does this once for each of the ten line-consuming checks (`jsonl_syntax.go:20`, `id_format.go:22`, `duplicate_id.go:26`, `duplicate_seq.go:27`, and the six `getTaskRelationships` callers), and once more for each `refreshSuggestion` call (`internal/doctor/cache_staleness.go:87`). §5.3 says every line-consuming check fails with *that* read error. §5.5 says no output points at `tick rebuild` while the read is incomplete. As built, both hold only if the I/O fault repeats the same way on 11 more open-and-read passes. A mid-read fault that doesn't recur every time is exactly the case the incomplete-read path exists for (a disk or mount failing mid-read). When it hits, an agent running `tick doctor` gets mixed pass and fail verdicts, plus the Cache check advising "Run `tick rebuild` to refresh cache" in the same report. The architecture agent reproduced this through `WithTasksOpener` with an opener that failed on odd calls. The file was opened 12 times: five checks passed, five failed with the read error, and the Cache check printed the rebuild advice. `TestDoctorIncompleteRead` (`internal/cli/doctor_incomplete_read_test.go`) can't catch this because its opener fails the same way on every open.
**Solution**: `RunDoctor` stores the whole scan outcome, lines and error together, through one doctor-owned helper (for example `doctor.WithScan(ctx, lines, err)`). This replaces the success-only `JSONLinesKey` write, and the lines-only key is retired so no caller can store a success-only outcome again. The key's preloading tests at `internal/doctor/jsonl_reader_test.go:218` and `:260` move to the helper. When an outcome is present, `getJSONLines` returns it, lines or error, and never re-scans. `ScanJSONLines` stays as the fallback only when no outcome was stored, which covers a check run on its own. This follows from §5.3's single "that read error" and §5.5's rule that nothing advises a rebuild while the read is incomplete: every check and `refreshSuggestion` must judge the same read. `linesUnavailableResult` keeps its shape. The Cache check's own byte read (`cache_staleness.go:28`) stays unchanged, as §5.5 and the §5.3 corrigendum freeze it.
**Outcome**: The line reader runs once per `tick doctor` run, and every line-consuming check and the Cache check's suggestion judge that one outcome. Take a fault that fails only the first read. Every line-consuming check reports the read error, and no suggestion names `tick rebuild`. A persistent failure no longer costs 11 more reads of a file that just failed.
