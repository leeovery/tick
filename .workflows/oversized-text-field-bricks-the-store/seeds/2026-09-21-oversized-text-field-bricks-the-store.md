# An Oversized Description Bricks The Project, And `tick doctor` Reports It Healthy

A task description large enough to push its JSONL line past 64 KiB is accepted and written, and from that moment every command that reads the store fails. `tick create "big" --description <70000 chars>` exits 0 and prints the new ID; the record lands in `.tick/tasks.jsonl` as a single 70,146-byte line, and the SQLite cache is rebuilt from those same bytes, so the freshness hash matches and nothing looks wrong. The next command tells a different story: `tick list`, `tick stats` and `tick rebuild` all fail with `Error: failed to parse tasks.jsonl: error reading JSONL data: bufio.Scanner: token too long`. `tick rebuild` failing is what closes the trap — the tool offers no route back to a readable project, and the user is left hand-editing the JSONL file to recover tasks that are still perfectly well-formed on disk.

The cause is a default nobody chose. The scanner that reads the store is constructed without a `Buffer` call, so Go's default 64 KiB `MaxScanTokenSize` applies, and every read path funnels through it — `ReadTasks`, `Rebuild`, and the `readAndEnsureFresh` used by both `Mutate` and `Query`. The write path has no matching limit, which is why the record gets committed in the first place: the value is marshalled and written before anything would have objected to its size.

**The diagnostic makes it worse rather than better.** `tick doctor` prints `✓ JSONL syntax: OK` and `No issues found`, exit 0, on a project that no other command can open. Its reader walks the file with the same kind of scanner and never consults `scanner.Err()` before returning, so the overlong line is silently dropped and the remaining lines — all well-formed — are handed back with a nil error. The syntax check then passes on what it was given. The storage reader does check its scanner's error; the doctor's does not, and the two disagree about the same file. Cache-staleness passes too, since the cache genuinely was rebuilt from the bytes on disk. This half is worth separating from the size limit: whatever cap is chosen, a health check that returns "healthy" for a store it could not fully read is wrong for every other reason a line might be unreadable — hand-editing, truncation, a partial write.

**Direction agreed, subject to its own discussion**: the fix is not to support arbitrarily large text. 64 KiB is far beyond anything a description needs, and unbounded free text in a line-oriented store is a standing liability. A reasonable fixed size limit on text fields — generous, but finite — enforced on the write path with a clear error, is the shape to explore. There is precedent in the codebase: note text is already capped at 2000 characters (`maxNoteTextLen`). Titles and descriptions carry no cap at all, which is the inconsistency to resolve. The doctor's silent-error half should be fixed regardless of where the cap lands.

How this was found: the `free-text-round-trip` review's change-set verification, probing that specification's §10.3, which declines to add a stdin or file input path for descriptions partly on the grounds that "an arbitrarily large description remains possible in principle". Measured against a built binary, it is not — past roughly 64 KiB it destroys the store. The defect is pre-existing and unrelated to that work: it reproduces identically with a binary built from `5a71cbc8` (the commit before the feature's first), and no commit in the feature's range touches `internal/storage` or `internal/doctor`. Source finding id `9-field-selection-10-free-text-that-begins-with-a-dash-1`.

Relevant ground: the scanner construction at `internal/storage/jsonl.go:95` and its error check at `:112`; the doctor's reader at `internal/doctor/jsonl_reader.go:37-66`, which returns at `:65` without checking; the read paths in `internal/storage/store.go` (`ReadTasks`, `Rebuild`, `readAndEnsureFresh`); the existing note cap in `internal/task/notes.go`; and the title and description validation in `internal/task/task.go`, which trims but does not bound. Note that if a cap is surfaced as a flag rather than a fixed constant, it has to land in `commandFlags`, `tick help` and the README together — `TestCommandFlagsMatchHelp` and `TestREADMEDocumentsFieldSelection` both enforce that.
